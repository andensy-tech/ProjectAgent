# Agent 复杂任务实现方案：单脑架构下的"认知脚手架"
> **状态**：已全部实施（Phase 1-3，2026-08-06 提交 ed44a21/96304ec/6a73102/ff935cd）。

> 设计文档 · 2026-08-05
> 背景：试用中发现 Agent 处理复杂任务时难以完成任务——①环境配置（MCP 配置/功能限制）导致工具失败；②缺乏复杂任务规划能力；③死循环时不与用户沟通获取进一步信息。
> 原则：不推翻"单脑+外设"架构（2026-05-28 刻意决策），在单脑上增加"认知脚手架"，让 LLM 看得见执行状态、能与用户协作、让引擎在僵局兜底。

---

## 一、现状痛点诊断

| 痛点 | 具体表现 | 代码根因 |
|------|---------|---------|
| **无元认知** | LLM 不知道自己在第几轮、已试过哪些失败、还剩多少预算，反复重试相同失败 | `engine.py` 循环只把工具结果追加进 messages，从不注入轮次/失败清单/剩余预算 |
| **无用户协作通道** | 信息不足、需要确认、陷入僵局时，LLM 只有"调工具"或"输出最终文本"，无法中途求助 | 5 个 Meta-Tool 无"问用户"工具；`AgentResponse.action` 前端无确认回调 |
| **无失败降级体系** | MCP 未配置/认证错/地址错 → 错误信息不可靠，被假错误误导空转 | 工具错误无统一分类；引擎不区分"配置问题 vs 业务问题" |
| **无规划结构** | 跨 Jira/Confluence/Gerrit 多步任务，LLM 每步"从零思考"易迷失 | 单脑循环无"计划→执行→检查"认知结构 |
| **无资源替代思维** | 首选数据源不可用即放弃，不会想"我还能用什么帮你" | 降级只"换工具"，不"换思路"；无替代资源清单 |

## 二、设计目标

1. **复杂任务**：可规划、可追踪、可收敛
2. **环境问题**：可感知、可引导、可降级
3. **僵局时刻**：可求助、可协作、可优雅退出
4. **能力不足**：目标导向的"尽力而为"，从力所能及的地方提供帮助
5. **执行过程**：智能自我纠错（反思→调整→验证）

## 三、核心设计：三层认知脚手架

```
┌──────────────────────────────────────────────────┐
│  用户                                              │
│    ↑ SSE: text/thinking/action/ask_user/...        │
│    ↓ 用户消息（含对 ask_user 的答复）               │
├──────────────────────────────────────────────────┤
│  引擎监督层 (Supervisor)  ← 新增职责，纯引擎逻辑    │
│  ├─ 执行状态追踪 ExecutionState                    │
│  ├─ 能力预检 + 可用替代资源清单 CapabilityPrecheck  │
│  ├─ 停滞检测 + 反思质量检测                        │
│  ├─ 失败分类 + 降级路由 ErrorTaxonomy              │
│  └─ 优雅退出 + 部分结果交付                        │
├──────────────────────────────────────────────────┤
│  LLM 循环（单脑，不变）                            │
│  ├─ 元认知注入：轮次/进度/已失败清单/剩余预算       │
│  ├─ 自我纠错：Reflect → Adjust → Verify            │
│  ├─ 资源替代思维：替代链①-④ 尽力而为               │
│  └─ 协作工具：ask_user / update_plan               │
├──────────────────────────────────────────────────┤
│  工具层 (MCP/Skills/Builtin)                       │
│  └─ 统一错误结构 {error_type, message, suggestion}  │
└──────────────────────────────────────────────────┘
```

**设计哲学**：Agent 定义为**"目标导向的尽力而为者"**而非"工具调用的执行器"。工具的完整与否只是手段，帮用户达成目标是目的。需 prompt 原则（替代思维、尽力而为）+ 结构（能力清单、替代链）+ 工具（多数据源通道）三管齐下。

## 四、十一个机制

### 机制 1：执行状态追踪（Execution State）
引擎维护轻量状态对象（在 `attempted_calls` 雏形上扩展）：
```python
@dataclass
class ExecutionState:
    rounds: int                 # 第几轮
    plan: List[str]             # LLM 首轮生成的子任务计划
    done: List[str]             # 已完成步骤
    blockers: List[str]         # 遇到的障碍
    failed_calls: Dict[str,int] # 相同调用失败次数
    last_progress_round: int    # 上次有实质进展的轮次
```
每轮 LLM 调用前在 messages 尾部**临时注入**（不污染持久化历史）：
```
[执行状态] 第 7/40 轮。已完成: 获取页面正文。已失败: confluence__get_page(404×2)。
计划剩余: 提取"项目分支链接"列 → 查 Jira 状态 → 汇总。
若已无可行路径，请调用 ask_user 向用户说明并征求方向。
```

### 机制 2：停滞检测（Stall Detector）
- 判定：连续 3 轮 `done` 无增长，或 `failed_calls` 同键连续失败且反思无变化
- 触发：降级路由（机制 3）或用户求助（机制 5）

### 机制 3：失败分类 + 降级路由（Error Taxonomy）
工具错误统一带类型标记：
```python
{"error_type": "config_error"|"auth_error"|"timeout"|"data_error"|"tool_unavailable", ...}
```
引擎按类型决策：

| error_type | 引擎动作 |
|-----------|---------|
| `config_error`（MCP 未配置/地址错） | 立即终止循环，yield `action` 卡片"打开设置页配置 MCP" |
| `auth_error` | 同上，提示检查凭据 |
| `timeout` | 重试（已有 `_call_with_retry`）→ 仍失败则降级 |
| `data_error`（页面不存在/无结果） | 提示 LLM：换数据源，或 ask_user 确认 |
| `tool_unavailable` | 尝试替代路径：MCP → 内置 → 直接说明限制 |

### 机制 4：能力预检（Capability Precheck）
循环开始前查用户 MCP 配置（复用 `capability.get_servers`），注入：
```
[能力状态] 已配置: jira(✓), confluence(✓), gerrit(✓)。未配置: 无。
[可用替代资源] 内置REST工具, 文档/OCR工具, 记忆, 用户上传文件
```

### 机制 5：用户协作工具（ask_user）★ 核心新增
新增第 6 个 Meta-Tool：
```json
ask_user(question, options: [...], timeout)
```
- LLM 何时调用：信息不足、关键决策（写操作）、僵局
- 引擎：`yield AgentResponse(type="ask_user", content=question, actions=options)`，结束当前流；用户答复作为新消息继续
- 与现有 `JIRA_CREATE_CONFIRM`/`_pending_plans` 统一
- 前端：新增 `ask_user` 消息类型 → 渲染问题+选项按钮

### 机制 6：首轮规划 + 进度追踪（Plan & Track）
- 复杂任务（多工具场景）引导 LLM 首轮输出简短计划
- 每轮末尾输出可解析进度标记 `{progress, blocked, next}`
- 引擎驱动停滞检测，LLM 偏离计划时提醒

### 机制 7：优雅退出（Graceful Exit）
替换"40 步但仍在继续"的无信息量失败：
```
已完成: 获取页面正文（表格提取 42 行）。
遇到问题: 查询 Jira 状态时 MCP 服务器超时 3 次。
建议: A. 稍后重试 B. 只汇总已获取的 CL 链接 C. 手动补充
```
附 options 让用户选方向。

### 机制 8：资源替代链（Substitution Thinking）★ 解决"尽力而为"
原则写进 AGENTS.md：**"无法用首选方式完成任务时，思考还有什么其他资源/途径能接近目标。"**
显式替代链清单：
```
① 替代工具层: MCP → 内置REST → 用户链接直接请求 → 推理
② 替代数据源层: Jira/Confluence → 用户上传截图/文档(OCR) → 记忆(memory_search)
   → 用户消息自带信息 → 让用户补充
③ 替代粒度层: 完整数据 → 部分数据(标注"仅N条不完整") → 方法论/模板
④ 兜底层: 诚实说明限制 + 手动步骤 + ask_user 征求方向
```

### 机制 9：自我纠错循环（Reflect → Adjust → Verify）★ 解决"智能纠错"
```
① Reflect（反思）: 失败后先想"为什么失败？参数错？地址/凭据错？数据源没数据？"
   每类失败对应不同修正策略，不盲目重试相同调用
② Adjust（调整）: 修正参数 → 换工具 → 换数据源(替代链) → 降粒度 → ask_user → 放弃
③ Verify（验证）: 给出最终答案前自检"用户核心诉求覆盖了吗？数据完整吗？格式可读吗？"
```
引擎配合：失败后 tool result 注入反思引导；完成前引导自检；停滞检测升级为"反思质量检测"（同一错误归因未变才判停滞）。

### 机制 10：部分结果交付（Partial Result Delivery）
即使失败也交付有价值的东西：
```
已完成: 页面正文已读取，表格提取 42 行 CL 链接。
未完成: 因 Jira MCP 超时，无法查询各 CL 的 Jira 状态。
你可以: A. 稍后重试 B. 先整理 CL 清单（部分交付） C. 导成 Excel 手动填
```
引擎保证至少交付"已完成部分"。

### 机制 11：优雅退出的补充——MAX_TOOL_ROUNDS 动态提示
- 第 10/20/30 轮注入"已用 N/40 轮，请评估收敛"
- 配合机制 1 的轮次注入，让 LLM 有预算意识

## 五、分阶段实施路线

| 阶段 | 内容 | 改动范围 | 风险 |
|------|------|---------|------|
| **Phase 1 元认知+收敛+纠错** | 执行状态追踪、元认知注入、停滞检测（含反思质量）、错误分类降级、反思引导、优雅退出+部分交付、能力预检注入 | 纯 `engine.py` + 工具错误标记 | 低，无前端改动 |
| **Phase 2 用户协作** | `ask_user` 工具、SSE 支持 `ask_user`、前端问题卡片、替代链 prompt（AGENTS.md） | 前后端 + AGENTS.md | 中 |
| **Phase 3 规划增强** | 首轮计划引导、进度追踪、自我验证钩子、项目管理典型任务模板 | 引擎 + AGENTS.md | 低 |

## 六、落点（对接现有代码）

- 执行状态注入：`engine.py` 循环头部，临时附加 system 层消息（不污染 messages 持久化历史）
- 错误分类：工具层返回统一结构 + `engine.py` 按 `error_type` 路由（`_execute_function_call` 的 except 已集中）
- `ask_user`：`AgentResponse` 新增类型 → `chat.py` SSE → `ChatPage.tsx` 新渲染分支
- 能力预检：`_build_tool_definitions` 已调用 `capability.get_servers`，顺带注入状态
- 停滞检测：复用 `attempted_calls`，加 `last_progress_round`

## 七、预期效果

- 环境配置问题 → 第 1-2 轮感知并引导用户配置，不再空转 40 轮
- 复杂任务 → 有计划、有进度、有降级，跨系统任务不迷失
- 僵局 → 主动 ask_user 求助，或优雅给出部分结果 + 方向建议
- MCP 能力不足 → 资源替代链尽力而为，交付部分结果而非失败
- 执行过程 → 反思→调整→验证，智能纠错而非盲目重试
